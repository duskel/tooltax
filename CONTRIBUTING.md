# Contributing to tooltax

There are three ways to contribute, in rough order of how often we expect them.

1. [Add an MCP server to the leaderboard](#1-add-a-server) -- one small JSON file.
2. [Add a lint rule](#2-add-a-rule) -- one directory.
3. [Add a tokenizer](#3-add-a-tokenizer) -- one file.

All three are designed so that CI does the reviewing. If the schema gate and the
tests pass, a maintainer only has to sanity-check that the server is real.

## Ground rules

- **Never commit a number tooltax did not measure.** Scores are generated by CI.
  Do not hand-edit `LEADERBOARD.md` or anything in `badges/` -- both are
  regenerated and your changes will be overwritten.
- **Never commit credentials.** The `env` field in a registry entry is for
  non-secret configuration only, such as a working directory or an endpoint. If
  a server cannot list its tools without a real API key, add it anyway and let it
  sit in the pending section; that is honest and useful.
- **No emoji** in code, docs headings, or CLI output.

## Setup

```bash
git clone https://github.com/duskel/tooltax.git
cd tooltax
npm install
npm run build
npm test
```

Node 20 or newer is required.

## 1. Add a server

Create one file at `servers/<owner>__<name>.json`, where `<owner>` is the GitHub
org or user and `<name>` is the server. Lowercase, with two underscores between
them.

```json
{
  "name": "Filesystem",
  "repo": "https://github.com/modelcontextprotocol/servers",
  "source": { "type": "npm", "package": "@modelcontextprotocol/server-filesystem", "args": ["/tmp"] },
  "category": "reference",
  "notes": "Tool list does not depend on the directories passed in."
}
```

Required: `name`, `repo`, `source`. Optional: `category`, `notes`.

`source` tells tooltax how to obtain the tool schema. Pick one:

| Type | Shape | tooltax runs |
|---|---|---|
| `npm` | `{ "type": "npm", "package": "pkg", "args": [] }` | `npx -y pkg` |
| `pypi` | `{ "type": "pypi", "package": "pkg", "args": [] }` | `uvx pkg` |
| `command` | `{ "type": "command", "command": "node", "args": ["server.js"] }` | the command |
| `url` | `{ "type": "url", "url": "https://..." }` | a static JSON schema, or a live MCP Streamable HTTP endpoint |
| `file` | `{ "type": "file", "path": "fixtures/x.json" }` | reads a checked-in schema |

Check your entry before opening a PR:

```bash
npm run build
node dist/cli.js validate
node dist/cli.js score npm:your-package
```

`validate` runs the same JSON Schema gate CI does. `score` confirms the server
actually starts and lists tools. If it does not, the entry is still welcome --
it lands in the pending section of the leaderboard with the reason attached.

The full field reference is `schema/server.schema.json`. Point your editor at it
for autocomplete.

### What you get back

Once merged, CI generates `badges/<owner>__<name>.json`, a shields.io endpoint
you can put in your own README:

```bash
node dist/cli.js badge npm:your-package --slug your-org__your-server
```

That prints the badge JSON and the markdown to paste. See
[the badge section of the README](README.md#get-a-badge-for-your-server).

## 2. Add a rule

A rule explains why a schema is expensive and how to fix it. Create:

```
src/rules/<rule-id>/
  rule.ts          the implementation
  meta.yaml        the same metadata, declaratively
  fixtures/
    trigger.json   a schema that MUST produce at least one finding
    clean.json     a schema that MUST produce zero findings
```

`rule.ts` exports a `Rule`:

```ts
import type { Finding, Rule, RuleContext } from '../../types.js';
import { option, savings } from '../lib.js';

export const rule: Rule = {
  meta: {
    id: 'my-rule',
    title: 'Short problem statement',
    severity: 'warn',          // error | warn | info
    category: 'structure',     // prose | structure | surface
    rationale: 'Why this costs tokens, in a sentence or two.',
    fix: 'What the maintainer should actually change.',
  },
  check(context: RuleContext): Finding[] {
    const limit = option(context.options, 'limit', 10);
    // context.tools, context.tokenizer, context.costs
    return [];
  },
};

export default rule;
```

Then register it in the `RULES` array in `src/rules/index.ts`.

Registration is explicit so the same code path works from source, from `dist/`,
and from a bundler. You cannot forget it: the contract test in
`test/rules.test.ts` reads `src/rules/` off disk and fails if any directory is
missing from the array.

That contract test also enforces, for every rule, automatically:

- `meta.id` matches the directory name
- `meta.yaml` matches the exported `meta` exactly, so docs cannot drift from code
- `severity` is valid; `rationale` and `fix` are substantive
- `trigger.json` produces at least one finding
- `clean.json` produces exactly zero
- an empty tool list produces zero findings
- a malformed tool does not throw

Write findings that a maintainer can act on. Name the tool and the path, quote
the offending text, and give a number:

```
search_documents: description is 118 tokens (budget 60): "This tool allows..." -- trim to roughly 60 tokens.
```

Set `estimatedSavings` conservatively. It feeds the headline "estimated
recoverable" figure, and an inflated one makes the whole report untrustworthy.
Use `0` when a finding is about correctness rather than cost.

Rules must not do network or filesystem I/O. They get the tools, a tokenizer,
and the per-tool costs; that is all they need.

## 3. Add a tokenizer

Create `src/tokenizers/<name>.ts` exporting a `Tokenizer`, then add it to
`TOKENIZERS` in `src/tokenizers/index.ts`:

```ts
import type { Tokenizer } from '../types.js';

export const myTokenizer: Tokenizer = {
  id: 'my-tokenizer',
  label: 'Human readable name',
  encoding: 'the-encoding',
  exact: true,      // false if this is a heuristic, which reports a warning
  count(text) { return 0; },
};

export default myTokenizer;
```

The contract test in `test/tokenizers.test.ts` picks it up automatically and
requires it to be deterministic, to return 0 for the empty string, to grow
monotonically, and to land in a plausible tokens-per-character range.

Set `exact: false` unless you are wrapping a real BPE implementation. Every
report built with an inexact tokenizer prints a warning, which is the point.

## Running things locally

```bash
npm run build          # compile to dist/ and copy rule assets
npm test               # vitest
npm run typecheck      # tsc --noEmit
node dist/cli.js validate
node dist/cli.js leaderboard --write     # regenerates LEADERBOARD.md and badges/
```

`leaderboard --write` launches every registered server. It takes a while and
needs network access. You do not need to run it in a PR -- CI does.

## Pull requests

- One logical change per PR. A server addition should not also change a rule.
- Run `npm test` and `npm run build` before pushing.
- Explain the reasoning behind a new rule's thresholds. "Because it felt right"
  is an acceptable answer if you say so; a fabricated justification is not.

## Reporting a wrong score

Open an issue with the server, the score tooltax reported, and what you believe
it should be. Include the output of:

```bash
node dist/cli.js score npm:the-package --json
```

Scoring methodology and its known limits are documented in the README under
[Methodology](README.md#methodology). If tooltax is measuring the wrong thing,
that is a bug worth fixing.
